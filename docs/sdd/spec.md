# 意图定义

## 1. 项目愿景

构建一个面向程序员和技术学习者的多用户知识学习社区，为用户提供：

- **技术问题提问与回答**
- **技术文章创作与阅读**
- **Markdown 技术文档**
- **标签化知识组织**
- **用户关注与社交关系**
- **个性化信息流**
- **内容搜索**
- **内容互动**
- **社区审核与治理**

最终形成一个：以技术知识沉淀、交流和学习为核心，以问答、文章和社区关系为主要载体的技术学习社区。

项目不仅关注功能完整性，同时重点体现：Go 后端工程能力、分布式系统设计能力、高并发处理能力、数据一致性设计能力以及系统可观测性。



---

## 2. 产品定位

项目不是简单的`Blog+Comment`，也不是单纯的`Stack Overflow Clone`，而是**程序员学习社区=问答+技术文章+社交关系+内容推荐+搜索+社区治理**

核心内容模型为两个相互独立的体系：
```
                 Knowledge Community
                         │
             ┌───────────┴───────────┐
             │                       │
          问答体系                  文章体系
             │                       │
        Question                  Article
             │                       │
          Answer                  Comment
             │                       │
          Comment                Interaction
             │
        Interaction
```
两套内容在数据模型和业务生命周期上保持独立，但共享：
```
User
Tag
Like
Collect
Comment
Report
Search
Feed
Notification
```

## 3. 核心用户角色

**普通用户 User**：
可以：
- 注册
- 登录
- 浏览内容
- 提问
- 发布文章
- 评论
- 点赞
- 收藏
- 关注用户
- 关注标签
- 举报内容

**内容管理者 Moderator**
负责：
- 内容审核
- 评论审核
- 举报处理
- 敏感内容处理

**管理员 Admin**
拥有完整后台管理能力：
- 用户管理
- 内容管理
- 评论管理
- 举报处理
- 标签管理
- 敏感词管理
- 数据统计
- 系统管理


---



## 4. 核心内容体系

**4.1 问答：**
核心结构：
```
Question
   │
   ├── Tag
   │
   ├── Answer
   │     ├── Like
   │     ├── Collect
   │     └── Comment
   │
   ├── Comment
   └── Report
```
用户可以：
```
提出问题
编辑问题
删除问题
回答问题
浏览回答
点赞回答
收藏回答
评论回答
举报问题/回答
```

**4.2 文章：**
文章是独立的内容体系
```
Article
   │
   ├── Author
   ├── Tag
   ├── Like
   ├── Collect
   ├── Comment
   └── Report
```
文章必须以 Markdown 作为主要内容形式,Markdown 是这个社区的核心内容表达方式，而不是一个可选的小功能。


---


## 5. 标签体系
标签是整个社区知识组织体系的重要组成部分，一个内容可以绑定多个标签，用户可以关注标签。

标签后续将参与：
```
内容分类
搜索
Feed
推荐
热门统计
用户兴趣建模
```
因此Tag不是简单的文章分类字段，而是整个系统的重要基础实体。


---



## 6. 用户关系
系统提供用户之间的关注关系：
```
User A
   │
   └── Follow
          ↓
       User B
```
形成：
```
Following
Followers
```
用户关系将参与：
```
Feed
推荐
通知
社交内容发现
```


---



## 7. Feed信息流

系统需要提供用户个性化内容流，至少包括：
```
推荐
关注
最新
热门
```
Feed 的内容来源包括：
```
关注用户发布的内容
关注标签相关内容
热门内容
推荐内容
```
**采用规则推荐，暂时不引入及其学习模型**

推荐因素可包括：
```
内容热度
标签兴趣
关注关系
内容新鲜度
用户行为
```

## 8. 搜索
系统必须提供全文搜索，搜索范围：
```
问题
回答
文章
用户
标签
```

核心能力：
```
关键词搜索
全文检索
分词
相关性排序
高亮
搜索建议
热门搜索
```

搜索系统与核心业务数据保持职责分离：
```
MySQL
   │
   │ Source of Truth
   │
   ▼
业务数据

Elasticsearch
   │
   │ Search Index
   │
   ▼
搜索数据
```
具体同步机制在plan.md中确定。


## 9. 内容互动
统一的内容互动体系：
```
Like
Collect
Comment
Report
```
需要覆盖：
```
Question
Answer
Article
Comment
```
其中点赞、收藏、关注等高频操作需要重点考虑：
```
幂等
并发
缓存
计数
数据一致性
```
这部分将作为项目重要技术能力之一。


---



## 10. 通知
系统需要提供站内通知，例如：
```
有人关注了你
有人点赞了你的回答
有人收藏了你的文章
有人评论了你的文章
有人回答了你的问题
你的内容审核结果
举报处理结果
```
通知系统将与kafka事件机制结合。

典型流程：
```
用户行为
   ↓
业务服务
   ↓
Domain Event
   ↓
Kafka
   ↓
Notification Service
   ↓
站内通知
```


---

## 11. 内容审核与社区治理
后台系统需要具备完整的社区治理能力。

**用户管理**
- 用户查询
- 用户状态
- 用户活跃情况
- 用户行为相关统计

**内容管理**
- 查看
- 审核
- 隐藏
- 删除
- 恢复

**评论管理**
- 查看
- 审核
- 删除
- 违规评论处理

**举报处理**
```
举报
 ↓
待处理
 ↓
管理员审核
 ↓
通过 / 驳回
 ↓
记录处理结果
```
**标签管理**
- 创建标签
- 编辑标签
- 合并标签
- 禁用标签
- 查看标签使用情况

**敏感词**
建立敏感词库：
```
敏感词
   ↓
内容提交
   ↓
文本检测
   ↓
通过 / 拦截 / 人工审核
```

**数据统计**
后台提供社区运营数据：
```
用户数量
活跃用户
新增用户
问题数量
回答数量
文章数量
评论数量
点赞数量
收藏数量
举报数量
内容增长趋势
```

## 12. 文件上传
**本地文件存储**，主要用于：
```
用户头像
文章图片
回答图片
Markdown 内容中的图片
其他社区附件
```
文件系统设计需要与业务数据解耦，业务数据库只保存：
```
file_id
file_name
file_path
file_type
file_size
```
而不直接把二进制文件塞进 MySQL。**后续可能会平滑迁移到oss中**，因此现阶段的文件存储设计需要预留抽象层。


---



## 13. 技术目标
**这个项目不是单纯追求功能数量，而是重点体现以下后端能力**
- **分布式系统：**微服务、服务发现、服务间通信、API Gateway
- **高并发：**Redia、缓存、限流、幂等、热点数据、高频互动
- **异步架构：**kafka、Domain Event、异步消费、重试、失败处理、最终一致性
- **搜索：**Elasticsearch、全文搜索、索引同步、搜索排序
- **数据库：**MySQL、事务、索引、联合索引、慢查询、分页、数据一致性
- **工程化：**Docker、日志、Metrics、Tracing、pprof、自动化测试
